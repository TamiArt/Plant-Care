# Как сделать PlantCare незаменимым помощником

## 1. Текущее состояние

PlantCare уже закрывает базовые сценарии:

> Обновление: базовое редактирование карточки и фото, интерактивные чек-листы заметок и подтверждение удаления уже реализованы.

- домашние и садовые растения;
- интервалы и история полива, опрыскивания и подкормки;
- заметки и ручные напоминания;
- сезонный чек-лист;
- редакционный каталог и научный поиск GBIF;
- пользовательские фотографии;
- переносимый JSON между устройствами;
- PWA и базовый офлайн-режим;
- необязательный бесплатный локальный ИИ-помощник.

Главный продуктовый пробел: приложение **записывает события**, но пока недостаточно помогает понять динамику конкретного растения, скорректировать его график и не потерять важные наблюдения.

## 2. Главная продуктовая цель

PlantCare должен отвечать пользователю на четыре вопроса:

1. **Что изменилось с конкретным растением?**
2. **Подходит ли ему установленный график ухода?**
3. **Какие наблюдения и действия уже помогали?**
4. **Как не потерять историю и продолжить уход на другом устройстве?**

Все решения должны работать бесплатно, локально и без обязательного аккаунта. Внешние справочники дополняют приложение, но не являются условием работы сада.

## 3. Приоритетный backlog

Оценка:

- **Ценность:** насколько функция помогает регулярно ухаживать за растениями.
- **Сложность:** относительная стоимость реализации после завершения модульного рефакторинга.
- **Приоритет:** `P0` — сделать сначала, `P1` — следующий слой, `P2` — развитие.

| Функция | Ценность | Сложность | Приоритет |
|---|---:|---:|---:|
| Редактирование имени и графиков ухода | Очень высокая | Низкая | P0 |
| Унифицированный журнал событий ухода | Очень высокая | Средняя | P0 |
| Локальные уведомления о задачах | Высокая | Средняя | P0 |
| Профиль условий растения | Очень высокая | Средняя | P1 |
| Адаптивный интервал полива | Очень высокая | Высокая | P1 |
| Фотодневник роста | Высокая | Средняя | P1 |
| Журнал симптомов и наблюдений | Высокая | Средняя | P1 |
| Офлайн-помощник по типичным проблемам | Высокая | Средняя | P1 |
| Пересадка, обрезка и размножение | Высокая | Средняя | P1 |
| Карантин и контроль вредителей | Высокая | Средняя | P1 |
| Структурированные инструкции каталога | Высокая | Высокая | P1 |
| Безопасность для детей и животных | Высокая | Высокая | P1 |

## 4. P0 — ежедневная полезность

### 4.1. Редактирование растения

Пользователь должен менять после добавления:

- имя;
- фотографию;
- место;
- интервал полива;
- интервал подкормки;
- необходимость опрыскивания;
- описание и внешнюю таксономическую привязку.

Перед удалением нужен confirm и короткая возможность отмены удаления. Архив предпочтительнее безвозвратного удаления.

### 4.2. Унифицированный журнал ухода

Вместо отдельных массивов действий постепенно перейти к общей модели:

```ts
type CareEventType =
  | "watering"
  | "misting"
  | "fertilizing"
  | "repotting"
  | "pruning"
  | "treatment"
  | "observation";
```

Каждое событие содержит дату, растение, заметку, необязательное фото и источник (`user`, `schedule`, `import`). Старый JSON мигрируется без потери истории.

### 4.3. Бесплатные уведомления

Использовать только доступные browser APIs:

- запрос разрешения только после явного действия пользователя;
- уведомления не являются единственным способом увидеть задачу;
- если фоновые уведомления недоступны, сроки остаются видны в существующих карточках растений и напоминаниях;
- настройки тихих часов хранятся в переносимом JSON.

Нельзя обещать гарантированные push-уведомления без бесплатной и устойчивой инфраструктуры.

## 5. P1 — персональный уход

### 5.1. Профиль условий

Добавить к пользовательскому растению:

- направление окна или уровень света;
- размер и материал горшка;
- наличие дренажного отверстия;
- тип субстрата;
- примерную влажность;
- комнатное/уличное размещение;
- дату последней пересадки;
- жизненную стадию: укоренение, рост, цветение, покой.

Поля необязательные. Приложение не должно заставлять заполнять анкету перед первым поливом.

### 5.2. Адаптивный интервал полива

Алгоритм работает локально и не использует AI API:

1. начать с пользовательского интервала;
2. вычислять фактический медианный интервал по истории поливов;
3. отдельно учитывать активный сезон и покой;
4. учитывать ручные изменения графика пользователем;
5. предложить корректировку, но не менять график без подтверждения;
6. объяснить причину предложения.

Не следует рассчитывать полив только по названию вида: условия конкретного горшка важнее общей карточки каталога.

### 5.3. Фотодневник

- несколько фото на разных датах;
- сравнение «раньше/сейчас»;
- привязка фото к пересадке, лечению или наблюдению;
- локальное уменьшение изображения перед сохранением;
- включение фото в JSON backup;
- предупреждение о размере хранилища.

Для этого потребуется IndexedDB: большие фото не следует продолжать хранить в `localStorage`.

### 5.4. Журнал симптомов

Пользователь отмечает наблюдаемые признаки, а не предполагаемый диагноз:

- пожелтение;
- сухие края;
- мягкие листья;
- пятна;
- вредители;
- замедление роста;
- опадение;
- состояние корней.

Симптом сопровождается датой, фото, последними событиями ухода и условиями. Это создаёт полезную историю даже без ИИ.

### 5.5. Офлайн-помощник по проблемам

Сделать проверяемое дерево решений на редакционных правилах:

- симптом → уточняющие вопросы → несколько возможных причин;
- для каждой причины — безопасная проверка и следующий шаг;
- уровень уверенности и явная пометка «не диагноз»;
- опасные химические рекомендации не выдавать автоматически;
- локальный ИИ может объяснять правила, но не заменяет их.

### 5.6. Пересадка, обрезка и размножение

Добавить отдельные события и планы:

- дата и размер нового горшка;
- состав субстрата;
- контроль через 7/14/30 дней после пересадки;
- обрезанные побеги;
- черенки и дочерние растения;
- связь «родитель → новое растение»;
- напоминание проверить укоренение.

### 5.7. Карантин и вредители

- статус «На карантине»;
- дата начала и причина;
- повторные осмотры;
- журнал обработок;
- список растений, стоявших рядом;
- дата безопасного завершения карантина.

Это особенно полезно для больших домашних коллекций.

### 5.8. Структурированный каталог ухода

Научная классификация GBIF не является инструкцией по уходу. Для редакционных карточек нужны отдельные проверяемые поля:

- свет;
- субстрат;
- температура;
- влажность;
- сезонность;
- пересадка;
- размножение;
- типичные проблемы;
- безопасность.

Каждый факт получает источник, дату проверки и статус `verified`, `estimated` или `unknown`.

### 5.9. Безопасность для детей и животных

Это высокорисковая информация. Добавлять её только из авторитетных открытых источников с attribution и датой проверки. Показывать отдельно:

- какое растение или часть потенциально опасны;
- для кого: кошки, собаки, дети;
- тип риска без назначения лечения;
- рекомендацию обратиться к ветеринару или врачу при факте контакта.

ИИ не должен самостоятельно генерировать утверждение о токсичности.

## 6. P2 — удобство большой коллекции

### 6.1. Календарь и статистика

- события по дням;
- выполнено/отложено/пропущено;
- средний фактический интервал;
- динамика новых листьев и цветения;
- растения, для которых график регулярно не подходит.

Статистика должна помогать корректировать уход, а не превращаться в соревнование.

### 6.2. Пакетные действия

Для коллекции из десятков растений:

- выбрать несколько растений;
- отметить общий осмотр или опрыскивание;
- перенести задачи на один день;
- фильтровать по комнате, месту и типу задачи.

Полив лучше подтверждать отдельно для каждого растения, чтобы не стимулировать механическое действие.

### 6.3. Расходники

Локальный список:

- грунт;
- перлит и дренаж;
- удобрения;
- горшки;
- средства обработки;
- срок годности и заметки.

Функция не должна содержать магазин, рекламу или партнёрские платные интеграции.

### 6.4. Архив и передача ухода

- архив погибших, подаренных и сезонных растений без удаления истории;
- экспорт отдельного растения;
- временная памятка для человека, который ухаживает за садом;
- импорт через существующий JSON без аккаунта и сервера.

## 7. Роль ИИ-помощника

ИИ — дополнительный интерфейс к локальным данным, а не источник истины. Полезные сценарии:

- объяснить ближайшие задачи простыми словами;
- суммировать историю выбранного растения;
- помочь сформулировать наблюдение;
- предложить вопросы для проверки причины проблемы;
- составить план восстановления на основе проверенных редакционных правил.

Ограничения:

- только бесплатная локальная/browser-модель;
- никакой незаметной отправки фото и заметок;
- ответы о токсичности и химических обработках только на основе проверенных карточек;
- отображать, какие локальные факты использованы;
- при отсутствии runtime приложение остаётся полноценным.

## 8. Рекомендуемый первый продуктовый срез

Следующая версия должна включать четыре взаимосвязанные функции:

1. редактирование растения и графиков;
2. единый журнал событий;
3. архивирование вместо безвозвратного удаления;
4. локальные уведомления как необязательное дополнение.

Этот срез создаёт ежедневный цикл:

> открыть растение → выполнить уход → записать факт → увидеть динамику → при необходимости скорректировать график.

После него имеет смысл реализовывать адаптивный полив, фотодневник и офлайн-разбор симптомов.

## 9. Метрики полезности без аналитического SaaS

Считать локально и показывать только пользователю:

- доля задач, выполненных или осознанно отложенных;
- насколько фактический интервал отличается от установленного;
- сколько растений не имеет актуального фото или условий ухода;
- сколько резервных копий создано и когда была последняя;
- сколько активных проблем остаётся без повторной проверки.

Никакая продуктовая аналитика не должна отправляться наружу без отдельного явного согласия.

## 10. Порядок реализации

1. Завершить модульный garden repository и миграции.
2. Ввести универсальную модель `CareEvent` с миграцией существующих историй.
3. Добавить редактирование растения и графиков.
4. Добавить архивирование и восстановление растений.
5. Подключить необязательные browser notifications.
6. После стабилизации repository перейти на IndexedDB.
7. Добавить фотодневник и журнал симптомов.
8. Реализовать локальные адаптивные рекомендации и дерево проблем.

Каждый пункт выполняется отдельным небольшим PR с `npm test`, `npm run build`, проверкой JSON round-trip и сохранением существующего дизайна.
