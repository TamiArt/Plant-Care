# Пошаговый план развития PlantCare

## 1. Непереговорные ограничения

1. **Не менять существующий дизайн.** Сохраняются текущие экраны, тексты, цвета, типографика, размеры, анимации, нижняя навигация и пользовательские сценарии. На этапах рефакторинга допустимы только исправления явных ошибок без визуального редизайна.
2. **Соблюдать модульность классического React-приложения.** Компоненты отвечают за отображение, hooks — за состояние и сценарии, repositories — за хранение, services/api — за внешние запросы, а чистые функции — за расчёты и преобразования.
3. **Только бесплатные решения.** Действует [`FREE_SERVICES_POLICY.md`](FREE_SERVICES_POLICY.md): никакого обязательного billing, платных API и trial-only сервисов.
4. **Не ломать офлайн-ядро.** Сад, история ухода, заметки, напоминания, локальный каталог, экспорт и импорт должны работать без внешних сервисов.
5. **Маленькие обратимые шаги.** Каждый этап завершается тестами и отдельным коммитом; нельзя одновременно переносить модуль и менять его поведение без отдельной причины.

## 2. Краткий план: 18 последовательных шагов

Ниже — основной рабочий порядок. Новый шаг начинается только после выполнения критерия готовности предыдущего. Все пункты выполняются без визуального редизайна.

| № | Шаг | Результат |
|---:|---|---|
| 1 | Зафиксировать regression baseline | Описаны критические сценарии, подготовлены fixtures `plantcare_v1` и JSON backup v1/v2, сохранены контрольные экраны при наличии browser runner. |
| 2 | Ввести единую команду качества | `npm run check` последовательно запускает unit-тесты, статические проверки и production-сборку; Vercel использует ту же проверяемую сборку. |
| 3 | Вынести shared utilities | Даты, ID и другие чистые helpers находятся в `shared/lib`, не зависят от React и покрыты unit-тестами. |
| 4 | Завершить garden model | Типы сада, расчёт сроков полива и миграции данных находятся в `features/garden/model`; `App.tsx` не содержит бизнес-расчётов. |
| 5 | Создать garden repository | Единственная точка чтения/записи локальных данных сообщает об ошибках и сохраняет совместимость с `plantcare_v1`. |
| 6 | Вынести `useGarden` | CRUD сада и синхронизация состояния находятся в `features/garden/hooks`; компоненты не обращаются к хранилищу напрямую. |
| 7 | Вынести компоненты сада | `PlantsScreen`, `PlantCard` и `UserPlantSheet` перемещены по одному, с прежними props, классами и внешним видом. |
| 8 | Завершить backup feature | `DataSheet` вынесен из `App.tsx`; JSON v2, merge/replace и миграция v1 проверены round-trip тестами на другом устройстве. |
| 9 | Завершить catalog feature P1 | GBIF client, hooks, mappers, detail panel и модальные окна разделены; пагинация, дедупликация, ошибки и offline fallback протестированы. |
| 10 | Улучшить бесплатный кэш каталога | Поиск и карточки GBIF кэшируются с TTL локально; источник, дата и attribution сохраняются без платного backend. |
| 11 | Завершить assistant feature | Плавающий помощник остаётся доступным справа внизу; UI отделён от локального Ollama/browser runtime, добавлены timeout и cancel. |
| 12 | Вынести care feature | Полив, опрыскивание, подкормка, сезонный режим и чек-лист оформлены как отдельная модель событий без изменения текущего UI. |
| 13 | Вынести reminders feature | Операции и отображение напоминаний изолированы и протестированы для сортировки, просрочки и повторных действий. |
| 14 | Укрепить PWA-обновления | Service Worker получает версионирование сборки, безопасное обновление и offline-ready/update-available состояния без внешнего SaaS. |
| 15 | Перейти на IndexedDB | После стабилизации repository растения и фото мигрируются из `localStorage` в бесплатную локальную IndexedDB; JSON экспорт остаётся обязательным. |
| 16 | Добавить бесплатные уведомления | Используются только Web Notifications и доступные browser APIs; отсутствие разрешения или поддержки не блокирует приложение. |
| 17 | Провести accessibility и performance аудит | Исправлены keyboard/focus/ARIA/reduced-motion без редизайна; удалены неиспользуемые зависимости, тяжёлые feature загружаются лениво. |
| 18 | Подготовить стабильный Vercel-релиз | Пройдены тесты, build, preview, offline/import-export smoke checks; `App.tsx` содержит только композицию feature-модулей. |

### Контрольные точки

- **После шага 2:** есть воспроизводимая проверка для каждого последующего изменения.
- **После шага 8:** пользовательские данные гарантированно переносятся через локальный JSON между устройствами.
- **После шага 10:** каталог остаётся полезным при нестабильном GBIF и не требует платных сервисов.
- **После шага 14:** установленная PWA безопасно получает новые версии с Vercel.
- **После шага 18:** монолитная декомпозиция завершена, а дизайн и persisted data сохранены.

## 3. Целевая архитектура

```text
src/
  app/
    App.tsx                  # только сборка приложения и верхнеуровневые состояния
    AppShell.tsx             # неизменяемая визуальная оболочка
    navigation.ts            # типы вкладок и URL-параметры

  features/
    garden/
      components/            # PlantsScreen, PlantCard, UserPlantSheet
      hooks/useGarden.ts
      model/types.ts
      model/watering.ts       # чистые расчёты сроков ухода
      repository/storage.ts  # чтение/запись и миграции
      index.ts
    catalog/
      components/            # CatalogScreen, CatalogDetailSheet, карточки
      api/gbif.ts
      hooks/useGbifSearch.ts
      model/mappers.ts
      data/editorial.ts
      types.ts
      index.ts
    care/
      components/            # checklist, fertilizer/misting actions
      model/events.ts
      model/season.ts
      index.ts
    reminders/
      components/
      model/reminders.ts
      index.ts
    backup/
      components/DataSheet.tsx
      model/backup.ts
      index.ts
    assistant/
      components/AiAssistantSheet.tsx
      services/localAssistant.ts
      index.ts
    pwa/
      hooks/usePwa.ts
      components/PwaStatus.tsx
      index.ts

  shared/
    components/              # переиспользуемые компоненты без бизнес-логики
    lib/date.ts
    lib/id.ts
    types/

  styles/                    # существующий дизайн без визуальных изменений
```

### Правила зависимостей

- `app` может импортировать `features` и `shared`.
- `features` могут импортировать `shared`, но не друг друга напрямую. Межмодульные действия передаются через props или верхнеуровневый orchestration hook.
- `shared` ничего не знает о бизнес-функциях.
- UI-компонент не обращается напрямую к `localStorage`, GBIF или Service Worker.
- Feature публикует внешний API через `index.ts`; внутренние файлы не импортируются из других feature.
- Чистые model-функции не используют React и browser globals, поэтому проверяются Node unit-тестами.

## 4. Подробный порядок реализации

## Этап 0 — контрольная точка перед рефакторингом

**Цель:** зафиксировать текущее поведение и гарантировать отсутствие визуальных изменений.

1. Составить список основных пользовательских сценариев: открыть вкладку, добавить растение, отметить полив, открыть карточку, создать заметку и напоминание, экспортировать/импортировать данные, найти растение.
2. Добавить smoke-тесты для чистых функций, которые уже можно вызвать без браузера.
3. Сохранить контрольные мобильные скриншоты ключевых экранов при появлении браузерного test runner.
4. Зафиксировать формат `plantcare_v1` тестовыми fixtures.
5. Добавить команду `npm run check`, объединяющую тесты и production-сборку.

**Готово, когда:** текущие сценарии описаны; `npm run check` проходит; для каждого следующего этапа можно проверить отсутствие регрессии.

## Этап 1 — общие типы и чистые функции

**Цель:** убрать из `App.tsx` независимую бизнес-логику без изменения JSX.

1. Перенести `todayStr`, `formatDate`, `daysSince` и генератор ID в `shared/lib`.
2. Перенести `PlantLocation`, `UserPlant`, `PlantNote`, `PlantReminder` и `WateringStatus` в `features/garden/model/types.ts`.
3. Перенести расчёт статуса полива в `features/garden/model/watering.ts`.
4. Перенести сезонные расчёты и советы в `features/care/model/season.ts`.
5. Добавить unit-тесты граничных дат, зимнего режима, просроченного полива и пустой истории.

**Готово, когда:** в `App.tsx` нет бизнес-типов и чистых расчётных функций; дизайн и DOM-структура не изменены.

## Этап 2 — модуль сада и repository

**Цель:** отделить хранение данных от UI.

1. Создать `garden/repository/storage.ts` с `load`, `save` и версионированными миграциями.
2. Не менять ключ `plantcare_v1` и формат данных без миграции.
3. Перенести `useGarden` в `features/garden/hooks/useGarden.ts`.
4. Заменить тихое игнорирование ошибки записи на типизированный результат repository; UI ошибки добавить позже без изменения визуального макета.
5. Перенести `PlantsScreen`, `PlantCard` и `UserPlantSheet` в `garden/components` по одному компоненту за коммит.
6. Открыть наружу только `useGarden`, необходимые типы и компоненты через `garden/index.ts`.

**Готово, когда:** `App.tsx` не читает `localStorage`, а все существующие записи пользователя проходят миграцию и открываются без потерь.

**Статус:** repository, `useGarden`, публичный API и основные garden-компоненты вынесены; `App.tsx` не работает с хранилищем напрямую.

## Этап 3 — завершение модуля каталога P1

**Цель:** закончить уже начатое разделение каталога.

1. Разбить текущий `catalog/gbif.ts` на API-клиент, mapper и hooks.
2. Перенести `GbifPanel`, `CatalogDetailSheet` и `AddToGardenModal` из `App.tsx` в `catalog/components`.
3. Переименовать `data.ts` в `data/editorial.ts`, не меняя содержимое карточек.
4. Сохранить пагинацию, отмену запросов и бесплатный GBIF fallback.
5. Добавить тесты:
   - первая и следующая страницы;
   - дедупликация;
   - ошибка сети;
   - истёкший кэш;
   - external taxon reference;
   - сохранение GBIF-растения офлайн.
6. Добавить attribution и дату получения там, где это уже предусмотрено текущим дизайном; новый визуальный блок не создавать без отдельного согласования.

**Готово, когда:** весь каталог находится в `features/catalog`, а отключение сети не блокирует редакционные карточки и пользовательский сад.

**Статус:** весь каталожный UI вынесен из `App.tsx`; последующая декомпозиция GBIF-клиента остаётся внутренней оптимизацией feature.

## Этап 4 — уход, чек-лист и напоминания

**Цель:** отделить действия ухода от карточек и хранения.

1. Вынести операции полива/опрыскивания/подкормки в `features/care`; полив остаётся прямым действием без дополнительной проверки почвы.
2. Вынести сезонный чек-лист без изменения его внешнего вида.
3. Вынести reminder types, операции и список в `features/reminders`.
4. Представить все даты ухода через общие model-функции, сохранив текущий persisted format.
5. Протестировать повторное действие в один день, сортировку напоминаний и просроченные даты.

**Готово, когда:** garden управляет растениями, care — событиями ухода, reminders — напоминаниями; визуально приложение идентично исходному.

## Этап 5 — резервные копии

**Цель:** сделать импорт/экспорт независимым и надёжным.

1. Перенести `GardenBackup`, validation, migration и JSON serialization в `features/backup/model`.
2. Оставить `DataSheet` только отображением и выбором файла.
3. Добавить тестовые fixtures старой, текущей, повреждённой и будущей версии backup.
4. Проверить режимы merge и replace, дубликаты ID и отсутствие обязательных полей.
5. Не подключать облачное хранилище: экспорт файла остаётся бесплатным и локальным.

**Готово, когда:** импорт повреждённого файла не меняет сад, а round-trip export/import сохраняет все данные.

## Этап 6 — PWA-модуль без редизайна

**Цель:** вынести PWA-логику и сделать обновления безопасными.

1. Переместить `src/pwa.ts` в `features/pwa/hooks/usePwa.ts`.
2. Вынести существующие install/offline элементы в `PwaStatus.tsx` с теми же классами и разметкой.
3. Добавить состояния `offlineReady` и `updateAvailable` в hook.
4. Версионировать Service Worker автоматически бесплатными build-инструментами либо build hash, не подключая SaaS.
5. Тестировать manifest и Service Worker статическими проверками; e2e добавить, когда доступен Chromium.

**Статус:** выполнено без изменения основного дизайна: PWA-модуль вынесен, добавлены состояния готовности офлайн-режима и обновления, Service Worker обновляется только после подтверждения пользователя, а manifest, Vercel headers и update-flow защищены статическими тестами. Автоматический build hash остаётся необязательной внутренней оптимизацией, потому что `/sw.js` принудительно ревалидируется Vercel, а навигация использует network-first.

**Готово, когда:** новая версия PWA не остаётся навсегда в старом кэше, а внешний вид install/offline UI не изменился.

## Этап 7 — локальный ИИ-помощник

**Цель:** изолировать необязательную бесплатную функцию.

1. Перенести Ollama/browser-model код в `features/assistant/services/localAssistant.ts`.
2. Описать capability API: `isAvailable`, `ask`, `cancel`.
3. Не добавлять OpenAI, Anthropic, Gemini API или другие платные облачные endpoints.
4. Основной интерфейс должен продолжать работать при полном отсутствии ИИ.
5. Добавить таймаут, отмену запроса и тест fallback-сообщения.

**Готово, когда:** `App.tsx` не знает, какой локальный runtime отвечает на запрос, и ни одна функция сада не зависит от ИИ.

## Этап 8 — финальная сборка App

**Цель:** оставить в `App.tsx` только композицию.

Ожидаемая ответственность `App.tsx`:

1. получить `garden` из feature hook;
2. хранить активную вкладку и верхнеуровневые modal targets;
3. передать callbacks feature-компонентам;
4. собрать `AppShell`, экраны и модальные слои.

Целевой размер `App.tsx` — ориентировочно 150–300 строк. Это ориентир, а не причина создавать бессмысленные файлы.

**Готово, когда:** в `App.tsx` нет API-запросов, `localStorage`, больших массивов данных, расчётов ухода и внутренних UI-компонентов.

**Статус:** выполнено — `App.tsx` содержит только presentation-адаптер каталога, верхнеуровневые состояния, callbacks и композицию feature-компонентов.

## Этап 9 — бесплатные улучшения после рефакторинга

Эти задачи выполняются только после стабилизации модулей и не должны менять дизайн без отдельного запроса:

1. IndexedDB вместо `localStorage`, с автоматической миграцией.
2. TTL-кэш GBIF в IndexedDB.
3. Дополнительные бесплатные открытые справочники после проверки лицензии и CORS.
4. Web Notifications в поддерживаемых бесплатных browser-сценариях.
5. Доступность: keyboard navigation, focus trap, aria-label и reduced motion без визуального редизайна.
6. Виртуализация большого каталога open-source библиотекой либо собственной реализацией.
7. Оптимизация bundle и удаление неиспользуемых зависимостей.

## 6. Проверки для каждого этапа

Минимальный обязательный набор:

```bash
npm test
npm run build
git diff --check
```

Дополнительно перед merge:

- локальный запуск `npm run dev`;
- проверка production preview;
- ручной проход затронутого сценария;
- сравнение текущего экрана с контрольным скриншотом;
- проверка offline fallback, если менялись каталог или PWA;
- экспорт тестового сада до изменения storage и импорт после него.

## 7. Что пока не делаем

До завершения модульного рефакторинга откладываются:

- визуальный редизайн и новая дизайн-система;
- платные или trial-only сервисы;
- облачные AI API;
- аккаунты и синхронизация;
- собственный backend только ради уведомлений;
- массовое добавление функций в монолитный `App.tsx`;
- смена persisted format без миграции;
- переписывание приложения на другой framework.
